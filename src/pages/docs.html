Stable links, readable names

Rename the heading; the ID keeps the link.

A heading is written for people. A stable ID gives tools and references a durable handle. Rename ## [DES-HERO] Hero Section to ## [DES-HERO] Room overview and references to [DES-HERO] can still resolve—as long as the ID and referenced file path remain valid.

spec.md · what 
| ID   | Requirement  |
| FR-1 | Hero section |
design.md · how 
## [DES-HERO] Hero Section
<!-- @see spec.md [FR-1] -->
source · why 
/** @see docs/specs/01-room-dashboard/spec.md [FR-6] */

These are shortened examples from the Room Dashboard project: the design points to FR-1, while its application source points to FR-6 and other requirements. Tasks use numbered groups such as 1.1 and can carry their own @see links. In VS Code, navigation and hover help you follow those references.

Keep IDs unique and stable; do not renumber or reuse an old ID when its meaning changes. Moving a file or changing an ID still requires its references to be updated and checked. A link records intent—it does not by itself prove the code meets it.

Before implementation

Four checks, four different questions.

The workflow separates several checks. Their exact rules depend on the document type and command.

01

Validate the spec

The full-spec validation checks required files, frontmatter, required sections, unique sequential requirement IDs, and links.

02

Validate design & tasks

Design checks anchors and traceability. Task validation checks task IDs, checkboxes, links, and whether requirements have task coverage.

03

Review & approve

Review uses agent judgment for ambiguity, gaps, risks, and readiness. Approval runs validation and review first, and is blocked while critical issues remain.

04

Verify implementation

After coding, check the actual changes and evidence against the agreed requirements. Human review and testing still matter.

In the full workflow, status moves Draft → Approved and later Superseded. Changing an approved spec’s scope bumps its version and returns it to Draft, and the design and tasks that depended on it need re-approval. Sprint uses ordered spec → design → tasks approvals in one file; editing an approved section sends it and every later section back to Draft. Dash is deliberately lighter and has no approval block. After implementation

Checks that say what they check.

AFX ships read-only quality gates as agent skills. They read your documents and code as text and report what they find.

Command What it looks at
/afx-check path Traces a feature from UI to action, service, repository, and database, and flags mock, placeholder, and TODO code.
/afx-check trace · links Audits @see annotations and cross-references between documents.
/afx-check schema · deps · coverage Database schema consistency in the design, the dependency graph from depends_on, and a two-way spec-to-code coverage map.
/afx-report orphans · coverage · stale Code without @see links, spec-to-code coverage, and specs not updated recently.
/afx-task verify One task against its spec: files exist, links resolve, no TODOs, a session entry recorded.

Every task carries two sign-offs: the agent’s and a human’s. The human box is never ticked while the agent’s is empty.

These gates never edit files or run your build or tests. A passing check means the text is consistent, not that the feature works. Run your tests and review the change.

Beyond the feature brief

Keep the investigation, the decision, and the reasons.

Research captures the question, findings, sources, analysis, and recommendations. An ADR records the context, chosen approach, rationale, alternatives, and consequences. /afx-research can promote a finding to an ADR or spec.

The journal is append-only. Each discussion gets a stable ID, and /afx-session capture can record the exact prompt, agent, model, and affected IDs behind a decision. /afx-context bundles spec state, task progress, and open questions for another agent, and /afx-next reads it all back to suggest one next step.
