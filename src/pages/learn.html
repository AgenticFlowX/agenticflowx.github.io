Code is cheap now. Agreement isn’t.

A coding agent can produce a feature in minutes. Without a shared, written intent it can also build the wrong thing, forget yesterday’s decision, or call the work done when nobody agreed what done means. A spec is the thing you and the agent both come back to.

A small plan is still a plan.

Use the shape that matches the work. They share stable references, reviewable intent, and a record of what happened.

Shape Use it for What you keep
Chat Questions, exploration, one-line fixes Nothing written down. Use Explore mode when you only want to read.
Dash A bounded fix or small change One feature-named .md file with Purpose, Tasks, and Work Sessions.
Sprint A feature with several implementation steps One feature-named .md file combining requirements, design, tasks, and work sessions, alongside journal.md.
Full spec Larger work with separate reviews and durable design decisions spec.md, design.md, tasks.md, and journal.md.

Move up a size when the scope calls for it. A Dash re-checks its scope as it works and recommends moving up when it sees ambiguous behaviour, several architecture choices, or security, migration, or public API changes. It never graduates silently. Graduating keeps task IDs, evidence, and Work Sessions, and retargets @see links. See file layouts and worked examples →

Try one real feature.

For example: let someone find a project by name, see a useful empty state, and clear the search. Agree on those behaviours before asking the agent to implement them.

  1. Investigate. Use Explore to find the relevant files and existing tests. Capture the constraints you discover.
  2. Start a Sprint. In Spec mode, ask for a Sprint, or run /afx-sprint new in your agent. The generated document is a draft for you to review.
  3. Make “done” concrete. Describe matching behaviour, empty results, keyboard use, and what is outside the scope.
  4. Review the plan. Refine requirements and design, validate their structure, review unresolved decisions, then approve the appropriate stage.
  5. Implement bounded tasks. Work through the planned file scopes and keep requirement links beside the code.
  6. Verify the result. Inspect changes, run the relevant checks, and test the actual behaviour before human signoff.

A full workflow separates document approval gates. Refine, validate, and review the spec before design; do the same for design before task planning. Approving runs validation and review and is blocked while critical issues remain. If an approved spec later changes scope, its version is bumped, it returns to Draft, and the documents that depended on it need re-approval. Implementation verification is a later, distinct check.

Work from the document.

The hybrid Markdown Previewer puts document and section actions beside the content: refine a requirement, resolve an open question, review the document, or start a task. Reading controls adjust font, tone, width, and focus.

Action Purpose
Refine Improve the living content or clarify one section.
Validate Check structure, IDs, metadata, and references.
Review Ask the agent to assess ambiguity, quality, risks, and missing decisions.
Approve Advance the document’s lifecycle gate after the relevant review.
Verify Check implementation evidence against the approved intent.

Actions vary by document type: tasks get Code, Verify, and Pick; a journal gets Note, Log, and Recap; a Dash uses the general reader without its own action bar. Actions that create content draft a command into chat for you to review; checks and approvals, such as Validate, Review, and Approve, run straight away. See every action set →

Quality Pulse and the Refinement Coach surface document gaps using heuristics. A healthy document score is not evidence that its implementation is correct.

Keep the reason, too.

Use research to collect findings and sources before choosing an approach. Use an architecture decision record when a decision needs its context, alternatives, and consequences preserved.

/afx-research helps investigate; /afx-adr records consequential decisions. Update living specs and designs when intent changes. Record the change and its rationale in the journal rather than letting chat become the only history.

For an unfamiliar repository, the extension’s Blueprint workflow can map findings in Explore. Review evidence and gaps, then save or update the map. Starting a Sprint from that context is a separate choice.

Finish with evidence, resume with context.

Use @see references to connect source code to requirement and design IDs. In VS Code, CodeLens, hover, and Cmd-click follow those links; /afx-check checks implementation paths, document links, and traceability. These are static checks the agent runs over text. They find broken links and placeholder code; they don’t replace your tests.

Tasks record execution and Work Sessions. Agent completion and human verification have separate signoffs. Inspect the evidence and test the behaviour before marking your part complete.

After the feature ships

Refine the living spec and design for the next change. Keep decisions and production notes in the journal, and new work in tasks.

At the next session

Open SDD Studio or Pipeline for status and next actions. Use /afx-next, session captures, and history recaps to recover context.
