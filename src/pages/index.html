Why spec-driven

The code is fast. The debt is faster.

Run the same prompt twice and you can get two different architectures. A spec doesn’t slow the agent down. It fixes what “right” means, so each run works toward a target instead of inventing one.

What the video covers

“Technical debt is future cost from present shortcuts.”

  • AI compounds it. Traditional software is deterministic; AI output is probabilistic and context-dependent, so a change anywhere can change everything, and debt grows faster.
  • Four places it hides. Data (bias, drift, poisoning), models (no versioning, evals, or rollback), prompts (undocumented system prompts, injection), and the organisation (no owner, no governance).
  • Not all debt is reckless. Strategic debt is taken on deliberately: documented, time-bound, with a plan to pay it back.
  • The fix is the basics. “Ready, aim, fire”: requirements, then architecture, then implementation, testing, deployment, and evaluation fed back into the requirements.

Where AFX fits That loop is what AFX writes down: requirements in spec.md, architecture in design.md, then tasks, verification, and a journal of the shortcuts you chose to take.

Living specs
Spec and design describe the system as it is now, in the present tense. They update in place; the history lives in the journal.
Approval
Approving runs validation and review, and is blocked while critical issues remain. Change an approved scope and it goes back to Draft for re-approval.
In the editor
Hover an @see to read the requirement, Cmd-click to open it, and get IDs autocompleted. A broken link shows as a ghost reference.
Honest limits
A link records intent. /afx-check finds broken links and orphans; whether the code is right still needs your tests and review.
